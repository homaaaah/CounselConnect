A campus without a configured location cannot offer `FACE_TO_FACE` or `BOTH`. A face-to-face appointment stores the campus location as a booking-time snapshot. |
| ADR-018 | A confirmed online appointment may create exactly one dedicated `APPOINTMENT` conversation when its scheduled start is reached. The Student and Counselor must match the appointment. `GENERAL`, `APPOINTMENT`, and `SOS` conversations remain separate, and face-to-face appointments cannot link a conversation. |
| ADR-019 | Authentication (approved 2026-09-05, formerly pending ADR-P01): Students sign in with student number; staff sign in with email. Passwords hash with Argon2id (existing bcrypt hashes verified and upgraded on next successful login). Web auth uses revocable MySQL-backed opaque sessions in a secure HttpOnly `counselconnect_session` cookie (256-bit random credential, SHA-256-stored) with a session-bound CSRF token (SHA-256-stored; `X-CSRF-Token` header on unsafe methods). Sessions idle-expire after one hour of no genuine user activity and absolutely expire 12 hours after creation with no sliding; background polls/heartbeats never renew activity. Login is allowed for `PENDING_VERIFICATION`, `ACTIVE`, and `VERIFICATION_EXPIRED` accounts (pending/expired students reach only account and re-verification functions); feature-level authorization still requires `ACTIVE` and valid enrollment where the docs say so. Password-reset credentials are hashed, single-use, expire in 30 minutes, and a successful reset revokes all active sessions without revealing account existence (flow implemented in its own task). No Remember Me in v1. **Students may sign in with their registered email or their student number (ADR-030).** |
| ADR-020 | Recurring Counselor availability (approved 2026-09-10, supersedes ADR-007's no-recurrence clause): Counselors configure recurring weekly schedules (`counselor_weekly_schedules`; ISO day 1 Monday–7 Sunday, `Asia/Manila` local `TIME` range, 15–240-minute whole slots, `ONLINE`/`FACE_TO_FACE`/`BOTH` mode; `FACE_TO_FACE`/`BOTH` require a configured campus Guidance Office location). Concrete slots materialize on demand from active schedules with `weekly_schedule_id` provenance; legacy/manual concrete slots remain valid. Counselors block temporary unavailable time (`counselor_availability_blocks`); a block never overlaps a `PENDING`/`CONFIRMED` appointment and never mutates appointments. Schedule edits deactivate the old row and insert a replacement; existing appointments/slots are unchanged. Overlap enforcement stays in the locked service layer (MySQL checks cannot compare rows). The Student `PENDING` request and Counselor decision flow from ADR-007 is unchanged. Implementation: migration `20260910_recurring_schedules`; tests in `test_recurring_schedules.py`. |
| ADR-021 | Appointment policies (approved 2026-09-10, resolves ADR-P04): booking horizon 60 days; slots keep materializing lazily from active weekly schedules on calendar/slot search (no background generation job in v1). Students may cancel/reschedule until 24 hours before the scheduled start; the assigned Counselor is unrestricted. No automated reminders in v1 (the appointments screen is the reminder surface). `NO_SHOW` is set manually by the assigned Counselor only, allowed from the scheduled start; no automatic no-show. For online sessions (when ADR-022 ships), joining is allowed from the scheduled start and closes 15 minutes after start. |
| ADR-022 | Real-time messaging transport (approved 2026-09-10, resolves ADR-P02): native FastAPI WebSocket endpoints with an in-memory connection registry (single-process modular monolith; no Redis/Celery). Messages persist through the existing messaging service under ADR-008 retention (bodies purged 30 days after closure). WebSocket traffic/heartbeats never renew session activity. `GENERAL`, `APPOINTMENT`, and `SOS` conversations stay separate (ADR-018). Appointment conversations open at the scheduled start within the ADR-021 join window. Implementation pending; this decision fixes the transport approach only. |
| ADR-023 | SOS implementation approach (approved 2026-09-10, resolves ADR-P03's technical half): the five-question instrument and rule thresholds remain hardcoded in one SOS module (no question/rule tables in v1, per the approved boundary); case records use `OPEN`/`RESPONDED`/`CLOSED` (ADR-010) and are retained for the current semester plus 30 days, then closed cases are purged except minimal audit metadata. The exact question wording, rule thresholds, and counselor availability/fallback rules are guidance-office content requiring human approval before the SOS module is built. |
| ADR-024 | COR evidence handling (approved 2026-09-10, resolves ADR-P05, ratifies implemented behavior): current-COR PDF only (`.pdf`, magic-byte checked), max 10 MB (`COUNSELCONNECT_COR_MAX_MB`, default 10), one open verification per Student, stored privately outside MySQL, deleted after decision or the seven-day pending TTL (ADR-004). Rejection requires the reviewer's comment; the notice shown to the Student is a single fixed, Counselor-editable template. The privacy notice is displayed at upload time. Audit events record minimal metadata (actor, action, verification id) — never file content. Implementation: `enrollment_verification` module; limits in `app.config`. **Human review workflow superseded by ADR-029**; file-policy limits remain. |
| ADR-025 | Expression-cue library (approved 2026-09-10, resolves ADR-P06): face-api.js via WASM, fully local/on-device, model weights lazy-loaded at first opt-in. Seven basic-expression label set; display only when confidence ≥ 60%; below that, show nothing rather than a low-confidence guess. Strictly opt-in per session, session-only, non-diagnostic, read-only context for the sitting Counselor, never persisted, and never influencing SOS logic (ADR-009). Devices that cannot run the model see a silent, graceful skip. |
| ADR-026 | Manual-resource publication rules (approved 2026-09-10, resolves ADR-P07): one Counselor approval publishes (no multi-step review; ADR-003 makes Counselor the authority). Attachments cap: 5 files per resource, 10 MB each, 25 MB total. External links must be canonical URLs and pass the existing allowed-domain check; manual resources never invoke the automated discovery scraper (ADR-011). |
| ADR-027 | Assistant implementation (approved 2026-09-10, resolves ADR-P08): deterministic retrieval only in v1 — keyword/category search over `PUBLISHED` resources plus approved navigation/FAQ content. No LLM provider, no generated prose, no persistent history (ADR-013). If the team later finds deterministic answers insufficient, revisit a bounded, history-free RAG provider as a new ADR. |

| ADR-028 | Scheduled online counseling (approved 2026-09-16): confirmation does not create a conversation. The appointment-derived launcher opens a lobby 30 minutes before start; a participant's explicit first join at or after start lazily creates the single `APPOINTMENT` conversation. REST is the durable source for messages/history and native WebSockets deliver committed events. The safety deadline is slot end plus 15 minutes; timeout closes chat with reason `TIMEOUT` but leaves the appointment `CONFIRMED` for the Counselor to record `COMPLETED` or `NO_SHOW`. Students may cancel/reschedule only until 24 hours before start; the assigned Counselor may change mode in place only before start and before chat activity. Closed history is Counselor-only until the 30-day body purge. Reminders use in-app/browser delivery only and contain no counseling content. |

| ADR-029 | Automated COR screening and self-confirmation (approved 2026-09-30; supersedes ADR-003's Guidance Staff COR-review duty and ADR-024's human review): the current COR remains the only enrollment evidence. On upload the backend screens the PDF in-request (format-marker score + OCR field extraction + embedded-barcode decode via configurable `pdftotext`/`pdftoppm`/`tesseract` and `zxing-cpp`). A screening becomes `AWAITING_CONFIRMATION` only when the format score and extraction confidence meet configured thresholds AND the barcode decodes and matches the extracted student number; otherwise it is `NEEDS_RESUBMISSION` for the Student to re-upload. The Student confirms the extracted academic fields (strict UCC student-number pattern `^\\d{8}-[A-Za-z]$`; campus/program must match existing active reference rows, never auto-created), which atomically activates the account with `valid_until` (12 months). There is no human approval queue; Guidance Staff retains no COR duty pending a future decision. Verified academic fields (student number, names, year level, section, academic year, and any campus/program the COR mapped to) are read-only during confirmation: the Student confirms or rejects, and a reject sets `NEEDS_RESUBMISSION`/`REJECTED_BY_STUDENT` for a re-upload; the backend also rejects any request that edits a verified field. The barcode's academic-period value is cross-checked against OCR, the decode result/confidence is recorded, and the enrollment-validity date printed on the COR is used for `valid_until` when still in the future (otherwise a 12-month default). Privacy is unchanged: COR bytes stay in the private store (10 MB, seven-day TTL) and are deleted after confirmation/resubmission; raw OCR text and raw barcode payloads are never persisted or logged (payload SHA-256 digest only); missing screening tooling fails closed (no activation). Residual risk: document self-consistency does not prove University issuance, so auto-activation is spoofable until an authoritative registrar source exists. Implementation: `cor_screening` module + migration `20260930_automated_cor_screening`; config in `app.config`. |

| ADR-030 | Process-flow fidelity (approved 2026-09-30): (7) Students may sign in with their registered **email or student number**; staff (Counselor, Guidance Staff, Superadmin) sign in with email. (8) A decoder/processing failure that cannot be attributed to the document is recorded as **`FAILED`** with a safe code (`TECHNICAL_ERROR`) and offers retry/support; unreadable/low-confidence/barcode-inconsistency remains `NEEDS_RESUBMISSION`. (9) The screening record enters **`PROCESSING`** (committed) before it is resolved, so the stage is observable. (11) A **`SUPERADMIN`** role is added (migration `20260930_superadmin_role` widens `chk_users_role`): it handles account recovery and operational exceptions, is read-only on the student directory, may reset a non-active Student to `PENDING_VERIFICATION` (`POST /accounts/students/{user_id}/recover`, audit `account_recovery`), and must not declare a COR authentic or approve registration. |

| ADR-031 | In-modal COR verification without auto-login (approved 2026-10-01): registration no longer signs the Student in. `POST /accounts/register/student-with-cor` and `POST /cor-screenings/resubmit` return a one-time `verification_token` (256-bit random, returned once, never in URLs); the client sends it in the **`X-COR-Token`** header to authorize `POST /cor-screenings/confirm\|reject\|resubmit` for that screening only. The token is stored only as a SHA-256 digest (`cor_screenings.verification_token_hash BINARY(32)` plus `verification_token_issued_at`; migration `20261001_cor_verification_token`), expires with the existing seven-day evidence window (no new TTL setting), is rotated on re-upload, and is destroyed on activation (`PASSED`) or TTL failure (`FAILED`). Missing/expired/tampered/rotated-away tokens fail closed with `401 INVALID_VERIFICATION_TOKEN` (generic message; the raw token is never logged) and token-bearing responses use `Cache-Control: no-store`. A present-but-invalid token never falls back to session auth; token requests are cookie-less, so CSRF does not apply. The signed-in `#registration` session path is retained as the fallback when the modal token is lost (closed tab). |
